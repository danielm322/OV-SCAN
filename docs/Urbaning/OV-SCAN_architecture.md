# OV-SCAN Architecture

OV-SCAN is a **LiDAR-only, open-vocabulary 3D object detector**: a closed-set, CenterPoint/TransFusion-style sparse-voxel detector produces class-agnostic 3D box proposals, and a separate **frozen CLIP-based alignment step** relabels each proposal with an open-vocabulary text string instead of a fixed class list. The whole thing is one `nn.Module` subclass, `OVScanLidar` (`pcdet/models/detectors/ov_scan_lidar.py:5`), built from `Detector3DTemplate.build_networks()` out of a fixed module list defined in `module_topology` (`detector3d_template.py:23-26`):

```
vfe → backbone_3d → map_to_bev_module → (pfe, unused) → backbone_2d → dense_head → (point_head/roi_head, unused)
```

`OVScanLidar.forward()` (`ov_scan_lidar.py:10-23`) just runs every module in that list in sequence, then either computes the loss (training) or runs `post_processing` (inference) — there's no other branching logic at the top level. Everything interesting happens inside `backbone_3d`/`backbone_2d` (the shared geometric feature extractor) and `dense_head` (the detection + open-vocab classification logic, including the alignment head).

## 1. Backbone: voxels → sparse 3D → dense BEV → 2D CNN

The backbone is really three stages chained together, each a config-selectable module:

**VFE (`MeanVFE`, `pcdet/models/backbones_3d/vfe/mean_vfe.py`)** — trivial voxel feature encoder: each voxel already holds up to `max_points_per_voxel` raw points; this just averages them (`sum / num_points`) into one feature vector per occupied voxel. No learnable parameters at all.

**3D backbone (`VoxelResBackBone8x`, `spconv_backbone.py:184-295`)** — a sparse-convolutional ResNet over the voxel grid, built with `spconv`. Structure:
- `conv_input`: one `SubMConv3d` (submanifold conv — preserves sparsity pattern) lifting raw voxel features to 16 channels.
- `conv1`–`conv4`: four stages, each a `SparseConv3d` with stride 2 (downsampling, `spconv_backbone.py:200-224`) followed by two `SparseBasicBlock`s (a sparse ResNet basic block: two 3×3×3 `SubMConv3d` + BN + ReLU with a residual add, `spconv_backbone.py:30-67`). Channel widths: 16→32→64→128 across the four stages — note this is the **Res** variant (`VoxelResBackBone8x`), which uses real residual blocks and a 128-wide final stage, versus the plain `VoxelBackBone8x` (also in the same file, unused here) which stops at 64.
- `conv_out`: one more strided `SparseConv3d` collapsing the remaining height dimension, producing `encoded_spconv_tensor` at **stride 8** relative to the voxel grid.
- Along the way it also stashes `multi_scale_3d_features`/`multi_scale_3d_strides` for all four intermediate stages — built for compatibility with multi-scale heads, but `OVScanHead` only ever consumes the final BEV map, not these.

**Map-to-BEV (`HeightCompression`, `height_compression.py`)** — the one genuinely "3D → 2D" step: takes the sparse `encoded_spconv_tensor`, densifies it (`.dense()`), and reshapes `(N, C, D, H, W) → (N, C·D, H, W)` — i.e. it folds the (now very short) remaining height/Z dimension into the channel dimension. This is what turns a sparse 3D feature volume into an ordinary dense 2D feature map (`spatial_features`) that a standard CNN can process.

**2D backbone (`BaseBEVBackbone`, `base_bev_backbone.py:6-112`)** — a small FPN-style CNN over the BEV map. Per the actual config used in this project (`LAYER_NUMS: [5,5]`, `LAYER_STRIDES: [1,2]`, `NUM_FILTERS: [128,256]`, `UPSAMPLE_STRIDES: [1,2]`, `NUM_UPSAMPLE_FILTERS: [256,256]`): two parallel "block" branches (one at the native stride, one downsampled 2×, each 5 conv layers deep), each upsampled back (`ConvTranspose2d` or a plain conv when `USE_CONV_FOR_NO_STRIDE` and stride==1) to a common resolution and **concatenated** channel-wise into `spatial_features_2d` — 512 channels total (256+256), at stride 8 relative to voxels. This is the feature map the detection head actually operates on.

So geometrically: raw points → voxelize → mean-pool per voxel → sparse 3D ResNet (stride 8, 16→128 channels) → height-collapse to dense BEV → 2-branch 2D CNN → 512-channel BEV feature map. Nothing here is open-vocabulary or CLIP-aware — it's a conventional closed-world 3D detector backbone; all the "open-vocabulary" behavior lives entirely downstream, in the head.

## 2. Head: `OVScanHead` — a TransFusion-style sparse query decoder

`OVScanHead` (`ov_scan_head.py:196-892`) is itself two halves bolted together: a **TransFusion-style center/query detector** (localization) and the **CLIP alignment pipeline** (open-vocab classification, §3 below). The detector half:

**1. Shared conv + heatmap head.** `self.shared_conv` (`ov_scan_head.py:240`) is a single 3×3 `Conv2d` projecting the 512-channel BEV map down to `hidden_channel=128`. `self.heatmap_head` (`:242-244`) is a small 2D conv stack (`BasicBlock2D` + a final `Conv2d`) producing a dense per-pixel, per-class heatmap — one of the `num_class` channels fires wherever the model thinks an object center of that class sits.

**2. Query selection via heatmap-NMS (`predict()`, `:395-460`).** Rather than predicting boxes everywhere, the head picks the top-`NUM_PROPOSALS` (200) heatmap peaks, across *all* classes jointly, as object queries:
- `heatmap.sigmoid()` is detached, then a `max_pool2d`-based local-maximum mask (`nms_kernel_size=3`) suppresses everything except local peaks — a cheap, learning-free NMS directly on the heatmap (`:405-421`).
- The resulting sparse heatmap is flattened over `(class, H, W)` jointly and `argsort`ed; the top 200 entries become this frame's 200 object queries, each query carrying a `(class, spatial index)` pair (`:424-429`) — this is why `NUM_PROPOSALS` is a hard *global* budget shared across every class, which is exactly the budget Phase 7/8/9's `van`-flood investigation turned on: if one class's heatmap channel fires too liberally, it can crowd out this shared top-200 slate.
- Each query's initial feature is gathered directly from the BEV feature map at its peak location (`query_feat`, `:430-433`), plus a learned per-class "category embedding" (`class_encoding`, a 1×1 `Conv1d` over the one-hot class, `:245,435-437`) added in — so a query already "knows" which heatmap channel it came from before any attention happens.

**3. Transformer decoder refinement (`self.object_decoder`, a `TransformerDecoderLayer`, `:248-251`, implementation in `transfusion_utils.py:29-101`).** This is a single standard transformer-decoder block (self-attention over the 200 queries → cross-attention of queries against the *full* flattened BEV feature map as keys/values → FFN), with learned sinusoidal-free position embeddings (`PositionEmbeddingLearned`, a tiny `Conv1d` MLP over raw (x,y) coordinates, `transfusion_utils.py:10-26`) added to both the queries' own BEV positions and the full map's positions before every attention op. This is exactly the TransFusion/DETR3D recipe: queries attend globally over the BEV map once, refining their feature using long-range context rather than only their local receptive field.

**4. Separate prediction heads (`SeparateHead_Transfusion`, `:17-51`, instantiated at `:255`).** The refined 128-dim query features feed a set of small independent 1×1 `Conv1d` branches, one per box attribute (`center`, `height`, `dim`, `rot`, `vel`, plus a `heatmap` branch re-predicting per-query class logits) — each a `num_conv`-deep stack of `Conv1d`+BN+ReLU (`heatmap`-named branches get their final-layer bias initialized to `-2.19`, the standard focal-loss negative-prior trick). Box center predictions are added back to each query's own BEV grid position (`:452`) — queries predict *offsets* from their heatmap peak, not absolute coordinates.

**5. Target assignment and loss.** During training, `get_targets_single` (`:560-648`) decodes every one of the 200 raw query predictions into actual 3D boxes (`decode_bbox(..., filter=False)`), then runs `HungarianAssigner3D` (`hungarian_assigner.py`) — genuine optimal bipartite matching (via `scipy.optimize.linear_sum_assignment`) between the 200 predicted boxes and the GT boxes, on a combined cost of focal-loss classification cost + L1 BEV-center distance + (negative) 3D IoU, weighted `0.15/0.25/0.25` per the config. Matched queries become positive targets; everything else is background. Four loss terms are summed (`loss()`, `:650-752`), each independently weighted:
- `loss_heatmap` — `GaussianFocalLoss` against a dense Gaussian-blob target heatmap built per-GT-box (`centernet_utils.draw_gaussian_to_heatmap`, radius scaled by box size) — this is the dense, pre-query-selection supervision signal, and precisely the component Phase 7/8 diagnosed as "over-firing" on the dominant class after fine-tuning.
- `loss_cls` — sigmoid focal loss on the 200 per-query heatmap-branch logits against their assigned GT class (or background).
- `loss_bbox` — L1 regression loss on the encoded box targets (`encode_bbox`, `:754-765`: normalized BEV offset, log-size, sin/cos heading, velocity), weighted per-dimension by `code_weights`.
- `loss_align` — covered in §3; always zero-gradient in this project (`align_weight: 0.0`).

## 3. Alignment head: open-vocabulary classification on top of a closed-set detector

This is the piece that makes OV-SCAN "open-vocabulary." Everything in §2 produces class-agnostic 3D boxes plus a 128-dim query feature per box; the alignment machinery's job is to turn that query feature into an open-vocabulary text label, by comparison against CLIP text embeddings — **without ever running an actual image through CLIP's vision tower at inference time.**

**Frozen CLIP, used only as a fixed text-embedding table.** In `__init__` (`:266-298`), the head loads a full CLIP model (`open_clip`, default `apple/DFN5B-CLIP-ViT-H-14`), **permanently freezes its visual tower** (`clip_img_encoder`, `requires_grad=False` + `.eval()`, `:269-275`) — and then never actually calls it anywhere else in the file. It's dead weight in the live forward pass; the only thing CLIP is actually used for at runtime is its **text tower**, run once at model-build time (`torch.no_grad()`, `:293-298`) to precompute a fixed matrix of L2-normalized text embeddings — one per open-vocabulary class string (e.g. "a type of car.", "a type of van.") — cached as `self.text_features` and reused for every single inference call afterward. A second, separate text-embedding set (`class_text_features`, `:352-356`) is also precomputed over the *coarse* `class_names` (used as the alignment head's query context, not for classification).

**`OVScanAlignmentHead` (`:78-194`) projects LiDAR query features into CLIP's embedding space.** This is a learned module (trainable in principle, though see below) that takes each query's 128-dim decoder output and its heatmap-predicted coarse class, and progressively upscales it to CLIP's 1024-dim embedding space through three stages of **cross-attention where the text embedding is the query and the object feature is the key/value** (`forward()`, `:152-194`):
- Stage 1: the coarse-class text embedding (projected 1024→128 via `text_embed_fc_1`) attends over the object feature (`upscale_mha_1`), residually combined and layer-normed, concatenated with the *original* object feature again, then expanded via an FFN to 256-dim.
- Stage 2: same pattern at 256-dim (text projected to 256 via `text_embed_fc_2`), expanding to 512-dim.
- Stage 3: same pattern at 512-dim (text projected via `text_embed_fc_3`), concatenated with the original 128-dim object feature one final time and linearly projected to the 1024-dim output (`self.out`).
Each stage re-injects the raw object feature (not just the attention output) before its FFN — a deliberate design so the final embedding doesn't drift arbitrarily far from the actual detected geometry just because the text query dominates attention. The output, `clip_preds`, is a 1024-dim vector per query meant to land near that query's true object's CLIP image embedding, *if* the object were actually photographed and encoded by CLIP's vision tower.

**Classification at inference is just cosine similarity.** `predict()` (`:462-477`) L2-normalizes `clip_preds`, multiplies by the precomputed text-feature matrix and CLIP's own learned `logit_scale`, and takes the argmax — standard CLIP zero-shot classification math, just with a learned LiDAR-feature embedding standing in for an image embedding.

**Two inference-time-only heuristics gate/adjust that argmax**, both config-driven, no training involved (`:300-349`, `:468-499`):
- `CONSTRAIN_TO_HEATMAP_BUCKET` / `HEATMAP_BUCKET_TO_VOCAB_KEYS`: a per-heatmap-channel routing table restricting each query's candidate vocabulary to only the open-vocab strings reachable from the coarse class its heatmap peak came from (e.g. the `car` channel's queries may only resolve to "car" or "van", never "pedestrian") — channels with no table entry get suppressed outright. This is exactly the mechanism behind `van` always being a fallback for noisy `car`-channel proposals (Phase 7 §5.1/Phase 8).
- `MARGIN_THRESH` / `RESCALE_BY_MARGIN_TEMPERATURE`: optional top-1-vs-runner-up logit margin checks — either hard-falling-back to a bucket default label when CLIP isn't confident, or softly down-weighting the box's score by `sigmoid(margin/T)` without changing its label.

**How the alignment head is actually "trained" (or isn't).** `loss()` (`:685-734`) implements a *selective* alignment loss: for each positive (GT-matched) query that happens to have an associated `gt_grounding_sam` crop, it loads a **precomputed** CLIP image embedding from disk (`torch.load(alignment_crop['object_embedding_path'])` — produced by some earlier, offline SAM-crop + real-CLIP-image-encoder pipeline, not by `clip_img_encoder` in this file) and computes a `CosineEmbeddingLoss` pulling `clip_preds` toward it. If no crop is available for any positive query in the batch (`gt_grounding_sam` is `None` for every box — true for every UrbanIng-V2X config in this project, since it has no SAM-grounding/camera data), it instead adds a literal `pred_dicts['clip_preds'].sum() * 0.0` dummy term (`:731-734`) — a zero-valued tensor kept in the graph purely so the alignment head's parameters stay part of the autograd graph (and don't trigger "unused parameter" errors under DDP), not to actually train it. Either way, the loss is multiplied by `align_weight`, which is set to **`0.0` in every config in this project** — meaning the alignment head's weights never receive a non-zero task gradient here; only the backbone + detection-head losses (`loss_heatmap`/`loss_cls`/`loss_bbox`) ever actually update parameters during fine-tuning. The alignment head's forward pass still runs every step (so it can still introduce *inference-time* behavior differences depending on what geometric features the backbone/decoder feed it), but its own weights are architecturally frozen-by-construction on any dataset lacking grounding-SAM supervision — which is the root cause behind why no LR, loss-weight, or backbone-freeze experiment in Phases 8/9 ever touched the confident `car`→`van` CLIP-mislabeling failure mode: fixing that would require either giving UrbanIng-V2X real grounding-SAM crops, or abandoning `align_weight: 0.0` and finding some other supervision signal for this specific head.
